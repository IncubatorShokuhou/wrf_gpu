Tools and commands

Everything runs through one program, gpuwrf. Only the forecast itself needs the GPU. The other commands work offline on the CPU with files you already have, and the ones that read history files accept CPU-WRF wrfout files as well as wrf_gpu output.

All commands

gpuwrf <command> --help shows every option of a command. The tools are tested on the CPU; they never change forecast results, and a statistics or calibration tool is not by itself a claim of better forecast skill.

Set up a forecast for your region

gpuwrf quickstart --profiles     # how large a grid fits on a 12-32 GB GPU
gpuwrf quickstart --bbox -17 28 -16 28.6 --resolution-km 9 \
  --date 2026-10-12T00 --hours 3 --case-dir work/tenerife --run

Without --prepare or --run the command only prints a plan. --prepare downloads the GFS data and runs WPS and real.exe; --run also starts the GPU forecast. Use a recent GFS cycle as the date. The region guide covers the container that builds WPS and WRF for you, the geography data and each step. Region set-up is Experimental: its preparation steps are tested on three areas, but GPU forecasts for new regions have not yet been compared with CPU-WRF, and the grid sizes from --profiles are estimates.

Check a case before running

gpuwrf doctor /path/to/case
gpuwrf manifest /path/to/case --output runs/case_manifest.json
gpuwrf reproduce runs/case_manifest.json --case-dir /path/to/case

doctor reports missing inputs, refused options, the time-step stability margin (CFL) and an estimate of GPU memory. manifest and reproduce let you prove later that a forecast used exactly these inputs.

Weather products

gpuwrf post --list-products
gpuwrf post --input runs/my_case/wrfout_d01_* --output runs/products.nc \
  --product wind10,precip,cloud --rolling-hours 3 6

Each product writes CF-annotated NetCDF variables. Thermodynamic products (thermal, instability, helicity) need the optional MetPy package and helicity needs --storm-u/--storm-v; the solar product needs pip install 'gpuwrf[apps]'. --product radar computes reflectivity, composite reflectivity, echo tops and vertically integrated liquid from the history fields.

Tune WRF for your region

Start with a control case and local observations. The regional tuning guide walks through station verification, surface parameters, physics selection, land cycling and ensembles, with each tool's qualification limits and costs. It also tracks the radiation, turbulence, atmospheric warm-start and initial-override tools under development for v0.4.4. Keep later dates out of tuning and score them separately.

gpuwrf override: checked input edits

Input overrides write new copies and record checks, masks and explicit waivers. Host/file behavior is tested; edited GPU forecast validation remains pending.

Soil porosity checks

The porosity helper checks already-loaded soil water against an explicit effective cap. It changes no arrays and does not qualify a new parameter scheme.

rad_diag and QI_BL: radiation diagnostics

Radiation history includes heating and the condensates passed to RRTMG; QI_BL exposes PBL cloud ice. Original-WRF tests and a three-nest GPU comparison are documented with their cost and limits.

icloud_bl: PBL clouds in radiation

icloud_bl controls the MYNN subgrid-cloud merge into radiation. It is one WRF value shared across nests, not a way to switch off MYNN itself.

MMINLU: Noah-MP land-use admission

The land-use check refuses unsupported non-MODIS inputs instead of silently using the wrong tables. Relabelling a dataset does not convert its categories.

Checkpoint branch and short forecast windows

Checkpoint branches use run --branch-from with a declared manifest. Short windows accept --minutes or --end-time; GPU branch validation is pending.

gpuwrf precompile: prepare a variant cache

The precompile queue plans work on CPU and primes programs through ordinary GPU forecasts when executed. Deviceless compilation followed by GPU loading is unavailable in v0.4.4; queue preparation does not install such artifacts.

topo_shading and slope_rad: terrain shading in nests

Terrain radiation keeps each nest's shadow height and WRF's separate shadow clock. Existing slope-plus-shadow cases intentionally change; the composed release's gate is separate from the original-WRF operator evidence.

Runtime parameter families: release status

Diffusion/damping parameter overrides (c_s, dampcoef, zdamp and related coefficients) are refused in v0.4.4 and may come in a later release after GPU qualification; no date or commitment. MYNN overrides such as sqfac ship as experimental: component and short two-domain GPU root checks passed; three-nest D6, stations and 24–72-hour drift are not qualified. The family status page explains these limitations. Existing static namelist support and the default forecast are unaffected.

nt_c and other Thompson coefficients

Thompson coefficients such as the droplet number nt_c change between runs through the same --runtime-parameters file, without a new compiled program for each value. They are gpuwrf extensions; WRF needs a recompiled module for the same test. Research candidate: CPU checks against original WRF and a GPU column check pass; the forecast-level GPU checks are pending.

tke_budget, bl_mynn_output and bl_mynn_edmf: MYNN budgets

The MYNN budget page writes WRF's TKE budget terms and EDMF plume profiles to history; bl_mynn_edmf=0 turns the plume mass flux off. Experimental and off by default: CPU checks against the original WRF driver pass; the composed GPU forecast check and its cost are pending.

cycle --native-atmosphere: atmospheric warm start

Atmospheric warm start carries a previous forecast's atmosphere, land and snow into a new run and follows WRF's cycling initialization. Experimental: checks against original WRF/WRFDA code and a CPU-WRF cycling reference pass; GPU initialization and forecast checks are pending.

Station verification and calibration

gpuwrf verify --stations stations.csv --obs observations.csv \
  --model runs/my_case/wrfout_d01_* --output-dir runs/verification
gpuwrf calibrate fit --stations stations.csv --obs past-obs.csv \
  --forecasts past-forecasts.csv --method bias --output station-model.json
gpuwrf calibrate apply --model station-model.json \
  --forecasts future-forecasts.csv --output corrected-stations.csv

verify downloads observations only with --fetch-observations metar or isd-lite; with --obs it stays offline. The station verification guide explains station heights, wind heights, land-aware sampling and precipitation intervals.

Ensembles

gpuwrf perturb --case CASE --output runs/wind-members \
  --members 5 --seed 451 --wind-std 0.05
gpuwrf ens prepare --mode batch --cases runs/wind-members/member-* \
  --output-dir runs/member_plan --hours 24
gpuwrf ens launch --plan runs/member_plan/plan.json
gpuwrf ens products --members members.json --variable T2 --output runs/ensemble_T2.nc

ens prepare also builds physics ensembles (--mode physics, one case with several namelists) and lagged ensembles (--mode lagged). ens launch checks GPU and host memory and runs as many members side by side as fit. ens verify gives probabilities, scores and reliability against station observations.

Two presets write the member namelists for you from one case:

gpuwrf ens prepare --mode stochastic --case CASE --members 10 \
  --schemes skebs,sppt --lengthscale-km 15 --hours 24 --output-dir runs/stoch
gpuwrf ens prepare --mode multiphysics --case CASE --members 7 \
  --hours 24 --output-dir runs/physics

--mode stochastic turns on WRF's stochastic physics (skebs, sppt, spp) with the same iseed_* and a different nens per member, as in WRF, and refuses combinations that would not perturb anything. --mode multiphysics takes rows of a table of physics combinations that passed the 24-hour comparison with CPU-WRF in v0.4.0; --schemes skebs adds SKEBS on top. Stochastic physics is Experimental: single-domain 24-hour runs pass the comparison with CPU-WRF using the same seeds (v0.4.1); nested runs are not checked yet. See the ensemble guide and the stochastic guide.

Choose physics for your region

gpuwrf optimize released --max-dom 1 --e41 PASS   # configurations a study may use
gpuwrf optimize plan --study study.json --output runs/study_plan.json
gpuwrf optimize run --study study.json --output runs/regional-study --chunk-minutes 60
gpuwrf optimize run --study study.json --output runs/regional-study --resume
gpuwrf optimize score --study study.json --forecasts forecasts.json --output runs/selection.json

A study lists candidate physics configurations, training dates and held-out test dates. Only the 47 complete physics sets that passed the v0.4.0 comparisons with CPU-WRF can be used; optimize released lists them (--e41 PASS keeps those without a code-quality note). New in v0.4.1, optimize run runs the forecasts on the GPU, as many at once as GPU and host memory allow, and can stop after a time budget (--chunk-minutes, exit code 3) and continue with --resume. Host memory, about 6–6.5 GB for each member that compiles, is usually the first limit. The result is a held-out comparison for your dates, not a validated choice of scheme. optimize identity prints the model version the study is bound to. The optimisation guide describes the study file.

Ensemble data assimilation (new in v0.4.1)

gpuwrf da check   --config da.json            # validates and lists every input
gpuwrf da analyse --config da.json --out analysis_00z
gpuwrf da cycle   --config cycle.json --out runs/da_cycle --dry-run

gpuwrf da combines an ensemble of forecasts valid at the analysis time with radiosonde, surface-station or table observations and writes an analysis wrfinput_d01 (LETKF for wind, temperature and water vapour; the dry column mass is held fixed). The analysis runs on the CPU. da cycle runs forecast/analysis windows with all members of a window in one process on one compiled program; on the GPU each further member then takes seconds instead of a fresh start. Experimental, outer domain only, no cloud or radiance observations. Better forecasts are not established, and the optional ensemble settings give too much spread in their test (prior spread about 2.3–2.6 times the actual error). See the data-assimilation guide, ensemble options and cycling in one process.

Noah-MP surface parameters without recompiling (new in v0.4.1)

The nine new soil/canopy/snow controls, including smcmax, dksat, hvt and rsmin, are refused in v0.4.4. Older surface controls such as z0mvt remain available; see the family limits.

JAX_PLATFORMS=cpu gpuwrf surface-params basis --input-dir CASE --output basis.npz
gpuwrf surface-params expand --basis basis.npz --output rough.npz \
    --class z0mvt:2=1.25 --set albdry=0.95      # entries without a prefix are d01
gpuwrf run --input-dir CASE --output-dir OUT --surface-controls rough.npz

gpuwrf run without domain options runs d01 only, so this control file holds d01 entries only. For a nested case, prefix entries with their domain (--set d02:albdry=0.95) and run all domains with --domains-from-namelist; a control for a domain outside the run is refused.

Eleven Noah-MP parameters (roughness, emissivity, soil albedo, leaf and stem reflectance, leaf and stem area, maximum vegetation fraction and two photosynthesis parameters) become runtime inputs of the compiled program, so every parameter set on one grid reuses it. Each control gives the same result as editing MPTABLE.TBL the same way; in a Swiss Alps 24-hour test with eight edited parameters, the GPU forecast changed like CPU-WRF with the same table edit (median response amplitudes within 1.5 %; patterns closest for surface properties and wind, looser for skin and 2 m temperature). Experimental: Noah-MP only; a resume with different controls is refused; the ensemble Kalman inversion tools (eki, osse) are checked on synthetic twin experiments only. See surface parameters.

Check compiled-program reuse (new in v0.4.1)

gpuwrf aot-key --input-dir /path/to/case_a \
  --compare-input-dir /path/to/case_b --json keys.json

aot-key loads a nested case on the CPU and prints the cache key of every compiled step program it would use: the outer domain, each nest, and inner domains compiled together with their nests. With a second case it prints SHARED or NOT SHARED per program and names the part of the key that differs. Shared programs are loaded from a cache or bundle prepared on the other case; the others are compiled. It compiles nothing and runs no forecast step; comparing two Tenerife three-domain cases takes about 6 minutes. Exit code 3 means a key could not be computed (shown as UNAVAILABLE, never as shared). Nested cases only; the keys carry the CPU target, so compare cases with each other, not with the file names in a GPU cache. In v0.4.1 every forecast date of one grid shares its programs, so a nested grid compiles once instead of once per date.

Since v0.4.2, aot-key works in a private temporary cache that is deleted when the command ends (also on Ctrl-C), so it never adds files to the compile cache or sealed bundle your settings point to; it prints a warning when they point into a sealed bundle. The keys are the same as with v0.4.1.

Export and station files

gpuwrf export --input runs/my_case/wrfout_d01_* --output runs/surface.nc \
  --format netcdf --variables T2 PSFC U10 V10
gpuwrf tslist-export --input runs/my_case/STATION.d01.TS --output station.csv

export also writes pressure levels (--pressure-levels), regional cut-outs (--region), Zarr and GRIB2 on an explicit grid (pip install 'gpuwrf[export]'). --raw keeps the native WRF dimensions and attributes.

Soil and snow cycling

gpuwrf cycle --source previous_cycle/wrfout_at_new_init \
  --wrfinput new_case/wrfinput_d01 --output new_case/wrfinput_cycled_d01

The source history must be valid at the new start time and on the same grid. The command writes a new file and never overwrites the template. Cycling is not data assimilation and is different from restarting a stopped forecast; see the cycling guide.

Several forecasts and several GPUs

scripts/run_parallel_cases.sh --out-root runs/batch CASE_A CASE_B CASE_C -- \
  --domains-from-namelist --hours 24
scripts/run_parallel_cases.sh --gpus all --out-root runs/ens MEMBER_01 MEMBER_02 -- \
  --domains-from-namelist --hours 24

Independent forecasts can share one GPU; the launcher starts as many as fit in memory, and one failed case never stops the others. With --gpus each forecast runs on one GPU of several. A single very large domain can also be split across GPUs with gpuwrf run --decompose 2x1. Experimental: both multi-GPU paths are tested on simulated devices only; no run on real multi-GPU hardware has been measured yet. See several GPUs.

Runtime tables

python -m gpuwrf.assets list      # every table and where it is found
python -m gpuwrf.assets fetch --all
python -m gpuwrf.assets verify

Large microphysics lookup tables, including the Thompson tables of the default physics, are downloaded on first use from the GitHub release and checked against pinned checksums. Runtime tables explains the cache and offline use.
