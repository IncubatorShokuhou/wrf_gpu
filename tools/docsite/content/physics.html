Physics options

wrf_gpu runs most WRF 4.7.1 physics schemes on the GPU. This page lists every option code of the seven physics selectors with its status; the selector statuses are those of v0.4.0, unchanged in v0.4.1 and v0.4.2. The codes are the same numbers you put in the &physics section of a WRF namelist.input.

What the status words mean

StatusMeaning
DefaultPart of the default physics suite (Thompson, MYNN boundary layer and surface layer, Noah-MP, RRTMG, with Kain-Fritsch cumulus on outer domains). This suite has the most testing: 24-hour comparisons with the original CPU-WRF on five real cases, including nested Canary Islands forecasts, and 72-hour runs in earlier releases.
Validated 24 hRuns on the GPU and passed a 24-hour comparison with the original CPU-WRF, started from the same input and judged against limits fixed in advance.
Validated 6 hAs above, but the accepted comparison covers six forecast hours.
ExperimentalRuns on the GPU but is outside the validated set: either it has no passing comparison, or it passed one outside the release test set. Its note says which.
CPU onlyImplemented and checked on the CPU; a GPU run refuses it.
Python API onlyUsable from Python with extra land inputs; gpuwrf run refuses it.
Not supportedgpuwrf run stops before the forecast with a message that names the option.

Notes used in the tables:

  1. Passed the comparison, but its compiled GPU code exceeds our code-quality limits for speed and robustness (for example large per-thread memory use). It runs correctly; its speed has not been measured and may be lower than with the default physics. The resource list names each case.
  2. Needs the Triton 3.6 compiler (pip install "triton==3.6.*"). The code-quality scan of its compiled GPU code could not be completed.
  3. Runs, but cannot be validated: the original WRF crashes on the test case at its first output. Use it with cu_physics=0.
  4. Passed a 24-hour comparison outside the release test set, and has the code-quality issue of note 1.

How the options were checked

The release check ran 66 configurations, each a scheme with a fixed set of companion schemes, compared hour by hour with the original CPU-WRF: 65 over 24 hours and the Goddard radiation pair over six hours. They are mostly single-domain forecasts; two-way nesting was checked on a two-domain case. Every option marked Validated 24 h or Default passed in one of them, and Goddard radiation is marked Validated 6 h. Options marked Experimental, CPU only, Python API only or Not supported are outside this check; their notes and status say why. Most configurations (51 of 66) used the bundled Swiss Alps case; options that need special surfaces, such as lakes, cities, open sea or wind farms, used cases that contain them. The validation page explains the method and the limits.

What a pass does and does not cover

A pass covers the tested configuration. It does not test every combination of schemes, and options outside the default suite have not been validated inside nested domains, except the YSU, Shin-Hong, ACM2 and EEPS boundary layers (v0.4.2, see below). The RUC land model (sf_surface_physics=3) is refused in nested runs. The support matrix records the exact configuration and companion settings behind each row.

Schemes that must be paired

As in WRF, some schemes only work together. gpuwrf run and gpuwrf doctor check this before the forecast and name the setting to change. The most common pairings:

  • QNSE: bl_pbl_physics=4 with sf_sfclay_physics=4.
  • TEMF: bl_pbl_physics=10 with sf_sfclay_physics=10, without a land model or with Noah-MP.
  • EEPS and KEPS (bl_pbl_physics=16/17): sf_sfclay_physics=1, without a land model or with Noah-MP.
  • Goddard radiation: ra_lw_physics=5 and ra_sw_physics=5 together, with Thompson microphysics and use_mp_re=1.
  • Ferrier microphysics (mp_physics=5/15): cu_physics=0.
  • Grell-family and Tiedtke cumulus: cudt=0, so the scheme runs every step.

New in v0.4.1, RRTMG (ra_lw_physics=4, ra_sw_physics=4) can take aerosol in the shortwave (aer_opt=1/3) and WRF's other radiation cloud fractions (icloud=2/3); the YSU and Shin-Hong boundary layers can use WRF's terrain correction of surface winds (topo_wind=1/2). Their status is on the namelist page. New in v0.4.2, icloud=0 runs RRTMG without clouds (namelist page); WDM6 (mp_physics=16) runs about three times faster with identical output.

Noah-MP options

With sf_surface_physics=4, the Noah-MP selectors of the &noah_mp namelist are read and checked. The default values are validated as part of the default suite. Of the other values, dveg=7/8/9, opt_run=8 and opt_infdv=1/2/3 passed 24-hour comparisons; the rest are Experimental.

Crop, irrigation, tile drainage and groundwater options need the matching geography from WPS (for example the groundwater fields for opt_run=5) and the original MPTABLE.TBL parameters. Surface mosaic (sf_surface_mosaic=1) is not supported. The Noah-MP options guide lists the inputs for each branch.

Lakes, cities, ocean and other surface options

The lake model, urban canopy models, the ocean mixed layer, SST updates and terrain-aware radiation are namelist features rather than physics selectors. Their status is on the namelist page.

Earlier releases

v0.3.4 and earlier ran a much smaller set of schemes; v0.3.3 and older could silently run the default schemes when a different one was requested. The v0.3.4 support matrix keeps that release's record.
