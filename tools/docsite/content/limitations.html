Boundaries and known issues

What wrf_gpu v0.4.1 does not cover yet, in plain words. The full technical record is in the repository's known issues and the support matrix.

What the validation covers

  • wrf_gpu is compared with the original CPU-WRF run from the same inputs, not with observations. The results are close to WRF, not bit-identical; small differences grow with forecast time, as between two CPU-WRF builds. No better or worse forecast skill than WRF is claimed.
  • Each option and feature marked validated was checked in one configuration: 65 configurations over 24 hours and Goddard radiation over six hours, mostly in single-domain forecasts. The default physics are the most tested. Experimental, CPU-only and Python-API-only options are outside these checks, and other combinations are not validated.
  • Fixed acceptance limits exist for the main fields (for example 2 m temperature, surface pressure, winds and accumulated rain). The other output fields are compared and reported, but have no limit.

Experimental and partly validated

  • Goddard radiation (ra_lw/ra_sw_physics=5) is validated over six hours, not 24.
  • Ferrier-Aligo microphysics (mp_physics=15) runs but has no reference: the original WRF crashes on the test case.
  • New in v0.4.1, experimental: topo_wind, aer_opt and icloud each passed a 24-hour comparison in the tested set-ups only. Data assimilation (gpuwrf da) works on the outer domain only, has no forecast-skill result, and its optional ensemble settings give too much spread. Surface-parameter calibration against real stations has not been done yet.
  • Experimental features: stochastic physics (24-hour single-domain comparison passed in v0.4.1), online diagnostics, station time series, regional output streams, LCZ urban land use, the 3-D TKE turbulence options, most non-default Noah-MP options and Zhang-McFarlane cumulus. See the namelist page.
  • Region set-up (gpuwrf quickstart) is tested on three areas, but GPU forecasts for new regions have not been compared with CPU-WRF.
  • Several GPUs: tested on simulated devices only; real multi-GPU speed is not measured.
  • FLG and GFDL radiation run on the CPU only.
  • Many validated schemes compile to GPU code that exceeds our code-quality limits for speed and robustness (marked 1 on the physics page). They run correctly, but their speed is not measured and may be lower than with the default physics.

Nests and inputs

  • Options outside the default physics are not validated inside nested domains. RUC land, the single-layer urban model, the 3-D TKE options and digital filter initialization are refused in nested runs. Moving nests are not supported.
  • Crop, irrigation, tile drainage and groundwater options need real geography from WPS; a missing field is refused, never filled with zeros.
  • WRF-Chem, WRF-Fire, WRF-Hydro, wave coupling, WRFDA variational data assimilation and adaptive time stepping are not part of wrf_gpu; the experimental LETKF (gpuwrf da) covers the outer domain only. The full list is on the namelist page.

Known numerical issues

  • Some schemes briefly produce tiny negative amounts of water or particle numbers inside a time step, before the same clean-up WRF applies. These events are counted and reported, not hidden; the output contains no NaN or infinite values.
  • The original WRF MYNN scheme reads one variable before setting it on a cold start (an upstream WRF bug). Where it matters, the comparisons use a WRF build in which this variable starts at zero; see the upstream WRF note.
  • P3, Jensen-ISHMAEL, WDM5 and NTU microphysics show small known differences from WRF's own arithmetic (rounding, diagnostics, small undershoots); their forecasts still pass the limits. The known issues describe each one.
  • Fixed in v0.4.1: up to v0.4.0, the default RRTMG shortwave computed the direct-beam surface flux (SWDDIR, and SWDDIF derived from it) from a different cloud optical depth than WRF; on cloudy daytime columns it differed by up to about 130 W/m². The horizontal total surface shortwave and the heating rates were not affected, but with slope radiation or terrain shading (slope_rad=1, topo_shading=1) the direct/diffuse split sets the shortwave reaching sloping ground, so on cloudy slopes the surface energy budget and the forecast could differ from WRF. v0.4.1 follows WRF; forecasts with slope radiation can change against v0.4.0.
  • For users of v0.3.0 to v0.3.4: those versions compiled the deep-soil temperature TMN of inner nests into the nested program but left it out of its cache key, so a compile cache shared between forecast dates could load another date's nested program without notice. The value differs between dates only over water, where it is masked out of the output. On the Tenerife three-domain grid, a 24-hour forecast run this way wrote all 72 history files byte-identical to a fresh compile; for the nine-domain Canary grid the same follows from identical land values, without an end-to-end run. With v0.3.x, set GPUWRF_AOT_VERIFY=1 when one cache serves several dates, or upgrade: v0.4.1 passes these inputs at run time. See the known issues.
  • Free-running open boundaries on wide domains (about 160 columns or more) can become unstable after roughly 14 hours; the normal boundary relaxation avoids this.

Performance and hardware

  • The speed and energy figures in the README charts were measured with v0.3.2 on one RTX 5090. v0.4.1 takes 4.4 s per forecast hour for the Canary Islands case (21× the 12-core CPU-WRF) and 6.1 s per case-hour for three Tenerife forecasts in parallel (20× CPU-WRF on 3 × 4 cores); energy was not measured again. See the release notes.
  • Only the RTX 5090 is tested. An NVIDIA Ampere or newer GPU is required; older cards (Pascal, Turing) are not supported.
  • The first run of a new grid or physics selection compiles the model, which takes minutes and more host memory than the forecast itself.

Release files

Large microphysics lookup tables, including the Thompson tables of the default physics, are downloaded on first use from the GitHub release and checked against pinned checksums. See runtime tables.
